# リモート画面の点灯とロック解除の確認

日付: 2026-10-31。メインコミット `65e82c0d01ac0f016db76cde4c76cb9a3c03183c` (0.1.16) に基づいています。

## 範囲と層別

- 携帯電話は、リモートで画面を明るくしたりロック解除したりするためにデフォルトでオフになっており、資格情報はコンピュータの接続設定ページでローカルにのみ構成できます。
- `core/device/DeviceAccess.kt` は、シリアル準備プロセスと実際のステータスの検証を担当します。プラットフォームの入力と識別は、Android の適応によって提供されます。
- `app/settings/DeviceAccessSettings.kt` 個別のキーストア キーを使用してアトミック ストアを暗号化し、非機密状態を保持し、復号化された資格情報をキャッシュしません。
- `McpDeviceTools` は、ステータス、明るい画面、およびロック解除インターフェイスを提供し、すべてのパラメーターを拒否し、元の MCP 認証を使用します。モデル ツール ディレクトリやタスク履歴には入りません。
- `TaskGate` は元のロジックを維持し、本当にロックが解除された後、自動的に解放されます。メイン画面のデバイス管理は、エージェント仮想画面から独立しています。
- 設定ページは、中国語と英語のリソースに対応する既存のグループ、行、ボタン、入力コンポーネントを使用します。古い認証情報の復元や表示は行わず、編集時にスクリーンショット禁止フラグを設定します。

./gradlew :core:test :app:testDebugUnitTest \
  :app:assembleDebug :app:assembleDebugAndroidTest

最終結果: コア 2416 項目、アプリ JVM 977 項目、障害なし、エラーなし。コア内の 2 つの元のテストがスキップされました。依存関係の方向、ドキュメントの一貫性、中国語と英語のリソース、オリジナルの回帰および新機能のテストをカバーします。

新しい検証範囲: デフォルトでオフ、アシスタントなし、最初のロック解除境界、冪等画面、コマンドは成功したが画面が実際には点灯していない、認証情報ロック画面なし、PIN/パスワード プロセス、入力後のワイプ、間違った認証情報後の永続的な一時停止、同時通話、キャンセル、待機中の手動ロック解除/権限取り消し、暗号化されたストレージとキーの紛失、認証情報の更新による古い要求の無効化、MCP パラメータ/認証制限、元のロック画面自己描画 PIN 制御と SIM/不明な制御の除外。

## Android 16 テスト機

は独立した Mika JP Dev (アプリケーション ID `com.wangzan101.mika.dev`、ローカルで変更されたアプリケーション ID を持つデバッグ パッケージ。この変更には含まれていません) によって検証されており、元のリリース バージョンとそのデータは保持されています。開発用 USB MCP は別のポート 18765 を使用します。元のモデルキーやその他の個人データはコピーされません。

ユーザーは、電話機で実際のロック画面の資格情報を構成するだけであり、テスト スクリプトは資格情報の読み取りや出力を行いません。レコードには、次の非秘密状態のみが含まれます。

|ステージ |インタラクティブ |キーガード_表示 |デバイスロック |準備完了 |
| --- | --- | --- | --- | --- |
|開始 |本当 |偽 |偽 |本当 |
|画面をオフにしてロックする |偽 |本当 |本当 |偽 |
|リモートで画面を明るくし、スリープ解除に戻ります |本当 |本当 |本当 |偽 |
|リモート PIN ロック解除によりロックが解除された状態に戻る |本当 |偽 |偽 |本当 |

送信前の永続的な占有が検出され、成功後に占有がクリアされました。これは、ロック解除状態を検出するだけでなく、資格情報の送信パスが実際にたどられたことを証明します。 オリジナルの Android ロック画面の

`pinEntry` は、編集可能として宣言されていない自己描画の `com.android.keyguard.PasswordTextView` です。識別ルールは、オリジナル バージョンの ID、クラス名、およびパスワードのフラグに従って解放されます。残りは、パスワード フラグと一致する入力タイプを持つ編集ボックスのみを認識し、回帰テストがあります。座標の死角は追跡されず、制御テキストは読み取られません。

`DeviceAccessSectionTest` 実機通過：二次入力確認、保存後の保存条件、入力値は表示されません。このテストでは、別のキャッシュからのシミュレートされたデータのみが使用され、実際の構成はカバーされません。最初のテスト ページは前面に表示されませんでした。終了後は開発版フォアグラウンドから再実行しました。結果はOK（1回のテスト）でした。検証後にテスト パッケージを削除します。

## 明らかに未検証の部分

- デバイス検証では、ユーザーの既存の PIN が使用されます。携帯電話のロック画面のタイプは変更されません。したがって、パスワードレス/スライドおよびパスワードのシナリオは自動テストの対象となっており、この実デバイスでの検証のために個別に切り替えられていません。
- パスワードは 4 ～ 64 個の印刷可能な ASCII 文字をサポートし、PIN は 4 ～ 16 桁です。パターン、SIM PIN、または不明なメーカーの認証情報ページはサポートされていません。
- は、再起動後の最初のロック解除前の既存の Mika JP MCP の起動をサポートしていません。
- の実マシン レコードは、「資格情報キーは SystemUI ウィンドウにのみ送信される」(`ShellService.injectTo`) の変更より前のものです。変更後、実機でPINロック解除を再実行し、ロック画面上に他のウィンドウがある場合、入力なしで`input_failed`が返されることを確認する必要があります。
- は、意図的に間違った PIN を実マシンに送信したわけではありません。失敗後の再試行の停止は自動テストによって検証されます。
- は、元のタスクの支払い/確認戦略を変更せず、検証用のモデルを構成したり、外部アプリ タスクを実行したりしませんでした。

携帯電話を使用する手順については、[コンピューターの接続手順](../mcp.md) を参照してください。
