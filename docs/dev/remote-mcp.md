# セルフホスト型リモート CLI/MCP

最初のバージョンの範囲: 単一ユーザー、単一デバイス、単一ゲートウェイ プロセス。ゲートウェイは HTTPS CLI/MCP 転送を提供し、携帯電話は WSS にアクティブに接続します。携帯電話の公衆ネットワークの受信ポートや追加の VPN は必要ありません。導入コードと英語の手順については、[tools/relay/README.md](../../tools/relay/README.md) を参照してください。

## の展開とペアリング

サーバーのドメイン名、Docker Compose、TCP 80/443 インバウンドを指すように準備します。ゲートウェイの HTTP ポート 8787 をパブリック ネットワークに直接公開しないでください。

```sh
cd tools/relay
cp .env.example .env
# 编辑 .env，设置 MIKA_DOMAIN，仅填写自己的域名，不带协议或路径
docker compose build
docker build --target caddy-check .
docker compose run --rm relay -init-owner-key -owner-key-file /data/owner-key
docker compose up -d
docker compose cp relay:/data/owner-key ./owner-key
chmod 600 owner-key
```

このマシン上で所有者キー ファイルを非公開で表示します。これは MCP トークンではなく管理キーであり、クライアント構成には入力されません。初期化によって古いキーは上書きされません。 Caddy は自動的に証明書を要求し、WebSocket をプロキシします。 Caddy のみがホスト ポートを公開します。ドメイン名とポートが到達可能である必要があり、データと証明書のボリュームが保持されている必要があります。

ブラウザでゲートウェイの HTTPS アドレスを開き、管理キーを入力して、[ペアリング コードの作成] をクリックします。ペアリング コードは 5 分間有効で、使用できるのは 1 回だけです。携帯電話の「設定→コンピュータに接続→リモート」にアドレスとペアリングコードを入力します。ペアリング後も、「リモート アクセスを許可」を明示的にオンにする必要があります。携帯電話を変更する前に、古いペアリングをキャンセルする必要があります。

### サーバーにはすでに Nginx がインストールされています

80/443 が既存の Nginx ですでに使用されている場合は、代わりに独立した [compose.nginx.yaml](../../tools/relay/compose.nginx.yaml) を使用し、デフォルトの Compose ファイルとマージしないでください。同じ .env を構成し、固定プロジェクト名で実行します。

```sh
docker compose -p mika-relay -f compose.nginx.yaml build
docker compose -p mika-relay -f compose.nginx.yaml run --rm relay -init-owner-key -owner-key-file /data/owner-key
docker compose -p mika-relay -f compose.nginx.yaml up -d
docker compose -p mika-relay -f compose.nginx.yaml cp relay:/data/owner-key ./owner-key
chmod 600 owner-key
```

ゲートウェイはサーバー 127.0.0.1:18787 にのみ公開します。 Nginx は同じホスト上に存在する必要があります。 [nginx.conf.example](../../tools/relay/nginx.conf.example) のドメイン名と証明書のパスを実際の値に変更し、独立した仮想ホスト構成として既存の http 構成に追加します。証明書はドメイン名をカバーし、更新と更新後のスムーズな読み込みの手配を備えている必要があります。まず、ドメイン名、マップ名、ポート 18787 の間に競合がないことを確認し、次に nginx -t を実行し、通過後にスムーズにリロードします。失敗した場合は、新しい構成のみが取り消されます。この例では、WebSocket アップグレードのアクセス ログを保存し、バッファリング、プロキシの再試行、および転送されたリクエストをオフにします。

後続のすべての Compose コマンドは、同じプロジェクト名と -f パラメーターを使用します。ロールバックする場合は、新しい仮想ホストを無効にし、Nginx を検証してスムーズにロードしてから、docker compose -p mika-relay -f compose.nginx.yaml down; を実行します。データ量を維持します。この展開では、バックエンド ポートをパブリック ネットワークにバインドしないでください。また、デフォルトの Compose ファイルを使用して Caddy を起動しないでください。

## クライアントと統合トークン

電話機には、LAN、リモート CLI、および MCP の両方に使用される `McpSettings` アクセス トークンが含まれるようになりました。ゲートウェイはトークンの生成、検証、ダイジェスト、または同期を行わず、透過的に `Authorization` を転送するだけであり、各リクエストは携帯電話 `RemoteAccess` によって検証されます。 LAN スイッチがオフになっても、明示的に開かれたリモート接続は引き続きこのトークンを使用できます。 USB 一時トークンは引き続きループバック エントリのみに使用され、リモート アクセスには使用されません。

- MCP: 携帯電話で「MCP → リモート」を選択し、カスタム認証リクエスト ヘッダーをサポートするクライアントに構成をコピーします。アドレスは `https://你的域名/mcp` です。
- CLI: 携帯電話で「CLI / Skill → Remote」を選択し、アクセス トークンをコンピューターのプライベート ファイルにコピーし、ページ上で接続コマンドを実行します。このコマンドにはトークン テキストが含まれません。

```sh
chmod 600 /path/to/token
mika connect --url https://mika.example.com --token-file /path/to/token
mika --url https://mika.example.com --token-file /path/to/token doctor
mika --url https://mika.example.com --token-file /path/to/token task list --limit 5
```

は、リモート呼び出しごとに `--url` および `--token-file` を渡す必要があります。 `mika connect` は接続を検証するだけで、リモート構成は保存しません。どちらのプロトコルも携帯電話上の同じタスク サービスにアクセスし、タスクの作成、クエリ、待機、応答、中断、キャンセルの動作はローカル エリア ネットワークと一致します。

### ゲートウェイ経由でのウェイクアップとロック解除: デフォルトではオフ

リモート ウェイクおよびロック解除を使用すると、トークンを保持している人が電話機でロック画面の PIN/パスワードを入力できます。 LAN では、同じネットワーク上のデバイスのみが携帯電話に接続できます。ゲートウェイを介してインターネット全体に接続でき、ゲートウェイ自体がトークンを確認できます。したがって、デフォルトでは、ゲートウェイを経由するリクエストは画面機能を確認できません (`mika_device_state`、`mika_wake_device`、`mika_unlock_device`、および `/api/v1/device`、および `/api/v1` の機能は `device_state` としてリストされません)。ツールとエンドポイントは、表示された後に拒否されるのではなく、まったく表示されません。ゲートウェイ経由でウェイクアップしてロックを解除するには、電話機で 3 つの項目すべてをオンにする必要があります。リモート ページの「リモート アクセスを許可」、「ゲートウェイ経由でのウェイクアップとロック解除を許可」（デフォルトではオフ、暗号化されたゲートウェイ設定に保存され、ペアリングまたは再ペアリング時にオフに戻ります）、および元の「リモート画面の照明とロック解除を許可」です。 LAN と USB の動作は変わりません。

携帯電話のアクセス トークンが置き換えられると、ローカル エリア ネットワークとリモート エリアの古いトークンはすぐに無効になり、ゲートウェイを同期する必要はありません。クライアントは構成を更新する必要があります。ペアリングの解除はデバイス チャネルを取り消すだけであり、アクセス トークンは置き換えられません。トークンを保持しているクライアントは、再ペアリング後も引き続きアクセスできます。これらのクライアントを無効にするには、電話機のトークンを置き換える必要があります。

ゲートウェイは、OAuth 認証の検出、登録、認可、または更新を提供しません。 OAuth フローのみを受け入れ、ベアラー要求ヘッダーを構成できないクライアントは、現在サポートされていません。ブラウザの Origin 要求は依然として電話によって拒否されます。既存の MCP はステートレス JSON を使用し、SSE を追加しません。

## スキーマと資格情報の責任

|資格情報 |目的 |予約済みの場所 |
| --- | --- | --- |
|モバイルアクセストークン |統合された CLI/MCP リクエスト認証 |モバイル暗号化ストレージ、ユーザー構成クライアント |
|デバイス チャネルの認証情報 |携帯電話をペアリングして WSS を確立し、ペアリングを解除する |携帯電話の暗号化ストレージ、ゲートウェイの概要 |
|管理キー |ペアリング コードの作成、ペアリング解除の管理 |ゲートウェイのプライベート ファイル、プロセス中の概要 |

`RemoteAccess.handle` 統合認証とプロトコルのエラー。その後、`RemoteEndpoints` と入力します。ローカル監視とリモートチャネルはタスクサービスを共有します。 LANプライベートアドレスチェック予約済み。リモート要求は非ループバック ソースを使用し、USB 許可を取得しません。障害冷却は発信者ごとに個別に記録されます。ゲートウェイは、確認した発信者アドレス (IPv4 アドレスまたは IPv6 の /64 プレフィックス) を要求とともに携帯電話に渡します。携帯電話は、ローカルで監視されているアドレスとは別に、「ゲートウェイ + 発信者」に従ってカウントします。発信者が連続して間違った推測をしても、発信者自体が冷めるだけです。クールダウン期間中は、正しいトークンを解放することさえせず、「正しい推測」を明らかにすることもありません。ゲートウェイがリバース プロキシの背後にある場合、すべての接続はプロキシから行われます。ゲートウェイがプロキシによって追加された最後の X-Forwarded-For から呼び出し元を取得できるようにするには、`-trust-proxy` を追加する必要があります (ダイレクト ピアがループバック アドレスまたはプライベート アドレスの場合にのみ読み取られます)。 2 つの Compose ファイルが追加され、Nginx の例ではこのヘッダーが `$remote_addr` で上書きされます。ゲートウェイ自体の管理キー、ペアリング、転送スロットルも同じ呼び出し元によってカウントされます。 `McpRuntime` は、リモート チャネルに携帯電話統合トークンを提供し、リモートがオフになっている場合はアクセスを拒否します。ペアリング自体ではリモートは有効になりません。

`RelayGateway` HTTPS アドレスとペアリング応答を検証し、リダイレクトに従いません。 `RelayClient` ホワイトリストは、`/mcp`、`/api/v1`、および `/api/v1/…` の GET/POST/DELETE を許可し、クエリ、認可、オリジン、X-Mika-Client、およびプロトコル ヘッダーを独立して保持します。各エンドポイントのメソッド、パラメータ、およびタスクの権限は、携帯電話によって引き続きチェックされます。ゲートウェイは、任意の URL または TCP をプロキシしません。

`RelaySettings` は、独立したキーストア キー暗号化、アトミックに保存されたデバイス構成を使用し、状態ストリームには非機密フィールドのみが含まれます。 `RelayNetwork` はネットワークの切り替えを感知し、`McpService` はフォアグラウンド サービスと通知を閉じるアクションに従います。アプリのガイダンスは、既存のコンポーネントと中国語、英語、繁体字中国語のリソースを使用します。ガイダンスを切り替えても権限は変更されず、トークンはコピー時に読み取り専用になります。

ゲートウェイ Web UI は Go テンプレートと埋め込みネイティブ CSS/JS を使用し、フレームワーク、ノード ビルド、CDN は使用しません。カラー マッチング、フォント サイズ、間隔、グループ カードとボタン サイズのマップ アプリのセマンティック値により、明るい/暗い色と狭い画面に適応します。英語、簡体字中国語、繁体字中国語の 3 つの辞書で、インターフェイス、エラー、フォーム検証、確認ボックスがカバーされています。これらはデフォルトでブラウザに従い、個別に選択できます。 Cookie は言語のみを保存します。管理キーはバックフィルされず、ペアリング管理はブラウザ認証情報ストレージを使用せず、JS なしで送信と確認が可能です。

## の切断とキャンセル

リモート チャネルを閉じ、すぐにチャネルを閉じてペアリングを維持します。ペアリングを解除するときは、まずデバイスを閉じてから、ゲートウェイにデバイス ID の削除を要求し、ネットワークが切断されたときの再試行のために閉じた状態を維持します。実行前にWeb UIの「携帯電話のペアリング解除」を確認する必要があります。

接続はバックオフされて再確立され、操作は再実行されません。各リクエストには独立した番号があり、同じ接続に対する繰り返し番号は実行されません。同時に最大 8 つのリクエストが可能で、ボディの上限は 1 MiB、各クエリとヘッダーの上限は 8 KiB、タイムアウトは 65 秒で、携帯電話で最大 50 秒のステータス待機をカバーします。携帯電話の結果が大きすぎる場合はエラーが返され、チャネルはキャンセルされません。

`device_offline` は使用可能なチャネルがないことを意味し、`delivery_unknown` は実行された可能性があるが結果が失われたことを意味します。タスクのステータスを照会する必要があります。タスクは自動的に再送信されたり、中断されたり、ロックが解除されたりしません。 CLI は、書き込みリクエストに対して HTTP 5xx で `outcome_unknown` を保守的に報告します。待機をキャンセルしても、実行されたアクションを元に戻すことはできません。オフラインでのコマンドのバックログはありません。

## の検証と運用保守

```sh
cd tools/relay
go test -race ./...
go vet ./...
cd ../..
./gradlew :core:test :app:testDebugUnitTest :core:cliTest :core:relayTest
./gradlew :app:assembleDebug :app:assembleDebugAndroidTest -PdevInstall
```

言語間テストでは、実際の Go ゲートウェイを起動し、本番環境の Kotlin トンネルと電話認証を介して実際の Python CLI と MCP を呼び出し、共有タスク、統合トークン ローテーション、USB トークンの拒否とペアリング解除を検証します。通常の JVM テストには Go は必要ありません。インターフェイス テストは `RelaySectionTest` および `ComputerAccessScreenTest` です。開発パッケージは、`devInstall` を通じて正式バージョンから分離されています。

`/healthz` は、ゲートウェイ プロセスが利用可能であることを証明するだけであり、携帯電話がオンラインであることを意味するものではありません。プロキシは、Host、WebSocket、および Protocol ヘッダーを保持し、呼び出し元アドレスで X-Forwarded-For をオーバーライドし、65 秒を超えるタイムアウトを設定し、自動リクエスト再試行を無効にする必要があります。デフォルトでは、本文や資格情報はログに記録されず、リバース プロキシも同様にログに記録する必要があります。バックアップにはデバイス ID が含まれており、古いバックアップを復元すると、取り消されたデバイスが復元される可能性があります。キーのローテーションを管理するには、携帯電話トークンを変更せずに、プライベート ファイルを置き換えてから再起動する必要があります。

HTTPS はゲートウェイ/プロキシで終端されます。ゲートウェイは技術的にリクエスト ヘッダーとタスクの内容を読み取ることができるため、信頼されたゲートウェイを使用する必要があります。このソリューションは、クライアントから携帯電話へのエンドツーエンドの暗号化ではなく、携帯電話認証の透過的な転送です。 PIN/パスワードは依然として電話でのみ処理されます。 Android のバックグラウンド制限、強制停止、ネットワーク切断、再起動は可用性に影響し、証明書、スタンバイ、ネットワーク切り替え、初回ロック解除の制限は個別に検証する必要があります。
