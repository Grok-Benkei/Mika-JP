# 自前ゲートウェイによるリモートCLI/MCP

利用範囲は所有者1人、スマホ1台、ゲートウェイ1プロセスです。ゲートウェイはHTTPSでCLI/MCPの要求を受け、スマホが外向きに接続したWSS経由で転送します。スマホ側の受信ポート公開や追加のVPNは不要です。実装と開発用コマンドは[tools/relay/README.md](../../tools/relay/README.md)を参照してください。

## 配備とペア設定

サーバーへ向けたドメイン、Docker Compose、外部から接続できるTCP 80/443が必要です。ゲートウェイのHTTPポート8787を直接公開せず、Caddy経由でHTTPS/WSSを提供します。

```sh
cd tools/relay
cp .env.example .env
# .envのMIKA_DOMAINに自分のドメインを指定する。スキームやパスは含めない
docker compose build
docker build --target caddy-check .
docker compose run --rm relay -init-owner-key -owner-key-file /data/owner-key
docker compose up -d
docker compose cp relay:/data/owner-key ./owner-key
chmod 600 owner-key
```

管理者キーファイルは手元で非公開に扱います。MCP用トークンとは別の認証情報で、チャット、クライアント設定、不具合報告には貼り付けません。初期化は既存キーを上書きしません。Caddyが証明書の取得とWebSocketの転送を担い、ホストのポートを公開するのはCaddyだけです。証明書を取得できるようドメインとポートを到達可能にし、データと証明書のボリュームを保持します。

ブラウザーでゲートウェイのHTTPSアドレスを開き、管理者キーを入力して「ペア設定コードを作成」を選びます。コードは5分間有効で、1回だけ使えます。スマホのPC接続設定から「リモート」を開き、ゲートウェイのアドレスとコードを入力します。ペア設定後も「リモートアクセスを許可」を明示的にオンにする必要があります。別のスマホへ変更する前に、既存のペア設定を解除してください。

### 既存のNginxと併用する場合

80/443をNginxが使用している場合は、独立した[compose.nginx.yaml](../../tools/relay/compose.nginx.yaml)を使います。既定のComposeファイルとは結合しません。同じ `.env` を用意し、プロジェクト名を固定します。

```sh
docker compose -p mika-relay -f compose.nginx.yaml build
docker compose -p mika-relay -f compose.nginx.yaml run --rm relay -init-owner-key -owner-key-file /data/owner-key
docker compose -p mika-relay -f compose.nginx.yaml up -d
docker compose -p mika-relay -f compose.nginx.yaml cp relay:/data/owner-key ./owner-key
chmod 600 owner-key
```

この構成ではゲートウェイをサーバーの `127.0.0.1:18787` にだけ公開するため、Nginxも同じホストで動かします。[nginx.conf.example](../../tools/relay/nginx.conf.example)のドメインと証明書パスを変更し、既存の `http` 設定へ独立した仮想ホストとして追加します。証明書は対象ドメインを含み、更新後にNginxを再読み込みできるようにします。

ドメイン・map名の重複と18787番ポートの競合を確認し、`nginx -t` が成功してから安全な再読み込みを行います。検査に失敗した場合は追加した設定だけを取り除きます。この例はWebSocketのアップグレードを維持し、応答のバッファリングとプロキシの自動再試行を無効にし、転送要求のアクセスログを残しません。

以後のCompose操作にも同じプロジェクト名と `-f` を使います。戻す場合は仮想ホストを無効にし、Nginxの検査と再読み込み後に `docker compose -p mika-relay -f compose.nginx.yaml down` を実行します。データボリュームは保持します。この構成でバックエンドを外部アドレスへ公開したり、既定構成のCaddyを併せて起動したりしません。

## クライアント接続と共通トークン

LAN、リモートCLI、MCPには、スマホの `McpSettings` にある同じアクセストークンを使います。ゲートウェイはこのトークンの発行・検証・ハッシュ化・同期・保存を行わず、`Authorization` を転送します。各要求を検証するのはスマホの `RemoteAccess` です。LAN接続をオフにしても、明示的に許可したリモート接続は使えます。USB専用の一時トークンはループバックだけに限定され、リモートでは使えません。

- MCP: スマホで「MCP」の「リモート」を選び、独自のAuthorizationヘッダーに対応したクライアントへ設定をコピーします。アドレスの例は `https://mika.example.com/mcp` です。
- CLI: 「CLI / スキル」の「リモート」から、スマホのアクセストークンをPCの非公開ファイルへ保存し、表示された接続コマンドを実行します。コピーされるコマンド自体にトークンは含まれません。

```sh
chmod 600 /path/to/token
mika connect --url https://mika.example.com --token-file /path/to/token
mika --url https://mika.example.com --token-file /path/to/token doctor
mika --url https://mika.example.com --token-file /path/to/token task list --limit 5
```

リモート操作のたびに `--url` と `--token-file` が必要です。`mika connect` は接続を確認し、リモート設定を保存しません。MCPとCLIは同じスマホのタスクサービスへ接続し、作成、照会、待機、回答、追加指示、キャンセルの動作はLAN接続と共通です。転送経路が増えてもスマホの権限は増えません。

### ゲートウェイ経由の画面点灯・ロック解除

既定では無効です。ゲートウェイ経由ではインターネットから接続でき、ゲートウェイ自体もアクセストークンを読み取れます。そのため、許可がなければ画面関連の機能を公開しません。`mika_device_state`、`mika_wake_device`、`mika_unlock_device`、`/api/v1/device` は利用できず、`/api/v1` の機能一覧にも `device_state` を出しません。

利用する場合は、スマホで次の3つをすべて有効にします。

1. 「リモートアクセスを許可」
2. リモート設定の「ゲートウェイ経由のスリープ解除とロック解除を許可」
3. 既存の「リモートでのスリープ解除とロック解除を許可」

2番目の許可は暗号化されたゲートウェイ設定へ保存し、ペア設定のたびに無効へ戻します。LANとUSBの動作は変わりません。

スマホのアクセストークンを変更すると、LANとリモートの旧トークンが直ちに無効になります。ゲートウェイとの同期は不要ですが、クライアント設定の更新が必要です。ペア解除はデバイス接続を取り消すだけで、アクセストークンを変更しません。同じトークンを持つクライアントは再ペア設定後も接続できるため、そのアクセスも止めたい場合はスマホのトークンを変更します。

ゲートウェイはOAuthの検出・登録・認可・更新を提供しません。独自のBearerヘッダーを設定できず、OAuthだけを要求するクライアントには対応しません。ブラウザー由来のOriginを持つプロトコル要求は、LANと同様にスマホが拒否します。MCPはステートレスなJSON応答を使い、SSEやセッションIDは追加しません。

## 認証情報と実装の役割

| 認証情報 | 用途 | 保存先 |
|---|---|---|
| スマホのアクセストークン | LAN・リモートCLI/MCPの共通認証 | スマホの暗号化ストレージ、利用者が設定したクライアント |
| デバイス認証情報 | WSS接続とペア解除の認証 | スマホでは暗号化保存、ゲートウェイではハッシュを保存 |
| 管理者キー | ペア設定コードの発行と解除 | ゲートウェイの非公開ファイル、プロセス内ではハッシュ |

`RemoteAccess.handle` が認証とプロトコルエラーを処理し、`RemoteEndpoints` へ渡します。LAN接続のプライベートアドレス制限は維持します。リモート要求はループバック以外の接続元として扱うため、USB専用の許可は得られません。

認証失敗による待機時間は接続元ごとに管理します。ゲートウェイが確認した接続元（IPv4、またはIPv6の/64プレフィックス）をスマホへ渡し、LAN接続とは別に「ゲートウェイ＋接続元」で数えます。連続して認証に失敗した接続元だけが制限され、その間は正しいトークンも拒否します。

リバースプロキシ配下では直接の接続元がプロキシになるため、`-trust-proxy` を使います。直接の接続元がループバックまたはプライベートアドレスの場合に限り、プロキシが追加した最後の `X-Forwarded-For` を採用します。両Composeファイルはこのオプションを指定し、Nginxの例はヘッダーを `$remote_addr` で上書きします。管理者キー、ペア設定、転送の回数制限も同じ接続元を使います。

`McpRuntime` はスマホの共通トークンをリモート経路へ渡し、リモートアクセスが無効なら拒否します。`RelayGateway` はHTTPSアドレスとペア設定応答を検証し、リダイレクトを追いません。`RelayClient` が転送できるのは `/mcp`、`/api/v1`、`/api/v1/…` のGET/POST/DELETEだけです。クエリと許可したヘッダー（Authorization、Origin、X-Mika-Client、プロトコル関連）を保持し、メソッド・引数・タスク権限はスマホで再検証します。任意URLやTCPの中継には使いません。

`RelaySettings` は専用のAndroid Keystoreキーで暗号化し、設定をアトミックに保存します。状態ストリームへは非機密項目だけを出します。`RelayNetwork` がネットワーク変更を検知し、`McpService` がフォアグラウンドサービスと通知からの停止操作を担います。案内ページの切り替えで権限は変更されず、コピー時のトークンは読み取り専用です。

### 日本語の管理画面

Goテンプレートと同梱CSS/JSを使い、Nodeのビルド、フレームワーク、CDNには依存しません。アプリの配色、文字、余白、カード、ボタンに合わせ、明暗テーマと狭い画面、キーボード操作に対応します。

管理画面、エラー、入力チェック、確認ダイアログは `web/ja.json` の日本語で表示します。`normalizeLanguage` と `pageLanguage` は常に `ja` を返し、ブラウザーの言語設定や古い言語Cookieでも他言語へ変わりません。言語欄も日本語だけです。Android側も日本語固定で、別言語への切り替え機能はありません。管理者キーを画面へ埋め戻したり、ブラウザーの認証情報ストレージへ保存したりしません。JavaScriptがなくても送信と解除確認ができます。

## 切断とペア解除

リモートアクセスをオフにすると接続を閉じ、ペア設定は保持します。スマホから解除する場合は、まずアクセスを無効にしてからゲートウェイへデバイス削除を要求します。ネットワーク要求に失敗してもアクセスは無効のままで、設定を残して再試行できます。管理画面の「スマホのペア設定を解除」には確認操作が必要です。

接続は待機時間を延ばしながら再確立しますが、操作は再実行しません。各要求には独立したIDを付け、同じ接続でIDが重複した要求は実行しません。同時要求は最大8件、本文は1 MiB、クエリとヘッダーは各8 KiB、タイムアウトは65秒です。スマホでの最大50秒の状態待機を含みます。応答が大きすぎる場合はエラーを返しますが、ペア設定は取り消しません。

`device_offline` は利用可能な接続がないこと、`delivery_unknown` は実行された可能性があるものの結果を取得できなかったことを示します。再接続してタスク状態を確認し、作成・追加指示・ロック解除を自動で再送しません。CLIは変更要求へのHTTP 5xx応答を保守的に `outcome_unknown` として扱います。待機のキャンセルで実行済み操作は元に戻りません。オフライン要求の蓄積も行いません。

## 検査と運用

```sh
cd tools/relay
go test -race ./...
go vet ./...
cd ../..
./gradlew :core:test :app:testDebugUnitTest :core:cliTest :core:relayTest
./gradlew :app:assembleDebug :app:assembleDebugAndroidTest -PdevInstall
```

結合検査は実際のGoゲートウェイ、本番用Kotlinトンネルとスマホ認証、Python CLI/MCPを使い、共通タスク、トークン更新、USBトークン拒否、ペア解除を検証します。通常のJVMテストにはGoは不要です。UIの検査は `RelaySectionTest` と `ComputerAccessScreenTest` です。`devInstall` は開発用アプリを公開版から分離します。

`/healthz` が示すのはゲートウェイプロセスの稼働だけで、スマホのオンライン状態ではありません。プロキシではHost、WebSocket、プロトコルヘッダーを維持し、X-Forwarded-Forを接続元で上書きし、タイムアウトを65秒より長くして、自動再試行を無効にします。ゲートウェイは本文や認証情報をログに残しません。プロキシでも同様に設定します。

デバイスID、管理者キー、証明書を整合した状態でバックアップします。古い状態を復元すると、解除済みのデバイスが復活する場合があります。管理者キーの更新は、32文字以上のランダムな秘密値を非公開ファイルへ設定し、プロセスを再起動します。スマホのアクセストークンやペア設定は変更しません。

HTTPSはゲートウェイまたはプロキシで終端し、転送するヘッダーやタスク内容を読み取れるため、信頼できるサーバーを使用してください。クライアントとスマホの間がエンドツーエンドで暗号化される方式ではありません。ロック画面のPIN・パスワードはスマホ側で扱います。Androidの待機制限、メーカー独自の制限、強制停止、回線切断、再起動で接続できなくなる場合があります。公開証明書、待機中の動作、回線切り替え、再起動後の初回ロック解除は配備先と実機で別に確認します。
