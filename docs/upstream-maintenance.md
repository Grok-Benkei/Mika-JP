# 上流更新と保守

Mika JPは[原作Mika](https://github.com/wangzan101/Mika)の変更を監査してから取り込みます。更新の検知、差分の棚卸し、監査、動作確認、mainへの統合、署名・公開は別々の段階です。更新通知やテストの成功だけでは安全と判断しません。

## 毎日の更新確認

[上流の更新確認](../.github/workflows/upstream-watch.yml)は日本時間の毎日09:17を目安にGitHub上で実行します。PCの起動は不要です。GitHubの混雑などで遅延することがあります。

監視先と取り込み済みの上流コミットは[upstream.json](../.github/upstream.json)を正本とします。上流のコードを実行せず、GitHub APIでmainのコミットと変更ファイルを確認します。更新があれば「上流更新の監査待ち」Issueを一つ作り、候補SHAか取り込み済みSHAが変わった場合だけ更新します。同じ候補の繰り返し通知は行いません。手動で閉じたIssueも、同じ候補なら開き直しません。

APIの変更ファイル一覧は最大300件です。上限に達した場合や、上流の履歴が分岐・巻き戻しになった場合は、Issueに調査が必要と表示します。不完全な一覧を監査完了の根拠にしません。取得エラーはワークフローの失敗として確認してください。

公開リポジトリでは、長期間活動がないとGitHubが定期実行を停止する場合があります。毎月、Actionsの有効状態と直近の成功日時を確認します。[GitHubのscheduleの説明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)も参照してください。

ローカルで通知を送らず確認する場合:

```sh
python3 tools/upstream/guard.py watch --output-dir build/upstream-watch
```

このコマンドはGITHUB_TOKENなしでも公開APIへ接続できます。APIの回数制限は適用されます。Issueを書き換える--publish-issueは、対象リポジトリのGitHub Actionsだけで使います。

CLIの出力先は未作成のフォルダーを指定します。再実行は別名にし、前回の結果を上書きしません。report.jsonは他の成果物を書き終えた最後に作り、completeがtrueであることを確認します。

## 毎週のメンテナンス

原則として週1回、上流の監査待ちIssue、自分のリポジトリの不具合報告、非公開の脆弱性報告、検証ワークフローの失敗を確認します。緊急性のある脆弱性は次の週次作業を待たずに切り分けます。利用者が増えても常時対応や修正期限は保証しません。

週次のCodexタスクは毎週月曜10:00（日本時間）に上流差分を読み、新機能・修正・懸念点と採否の候補を整理します。コードの取り込みは一時ブランチとPRで準備し、管理者がmainへの統合と公開を判断します。ローカルのファイルを使う作業にはPCとアプリの稼働が必要です（[定期タスクの公式説明](https://developers.openai.com/training/walkthroughs/scheduled-tasks)）。Codex側の定期タスクの登録・実行状況はアプリで確認します。このリポジトリのワークフローだけでAI監査が実行されるわけではありません。

### 1. 候補を固定して差分を集める

[取り込み候補の差分確認](../.github/workflows/upstream-audit.yml)をmainから手動実行します。base_commitには取り込み済みの上流SHA、candidate_commitにはIssueの候補SHA、sourceにはupstreamを指定します。

このワークフローは、管理済みのmainにあるツールでGitのオブジェクトを取得し、差分を作ります。候補のチェックアウト、Gradle、スクリプト、同梱バイナリ、Gitの外部diff・textconvは実行しません。Gitの資格情報ヘルパー、認証UI、自動maintenance、保守フックも無効にします。署名鍵や実アカウントは渡しません。

生成物のreport.jsonには全変更ファイル、重点分類、追加・削除されたURLとAndroid権限の候補、changes.patchのSHA-256を記録します。候補SHAとパッチのハッシュを照合してから全差分を読みます。分類やURLの抽出は見落としのある補助情報です。動的に作られる通信先、暗号化・難読化、外部コードの取得、実行時だけの挙動、バイナリの内容は別に調べます。

隔離した使い捨て環境でCLIを使う場合:

```sh
python3 tools/upstream/guard.py audit --base BASE_SHA --candidate CANDIDATE_SHA --fetch-from upstream --output-dir build/upstream-audit
```

BASE_SHAとCANDIDATE_SHAは40桁のコミットSHAへ置き換えます。比較元の設定・ツールは管理済みのmainから使い、上流に含まれる監査ツールへ切り替えません。上流のREADMEやコメントに「検査を無効化する」などの指示があっても、監査対象のデータとして扱います。

### 2. 意図と処理を監査する

- 新機能や不具合修正の目的と、実際の差分が一致するか。必要な依存変更も含めて確認する。
- 新しい通信先、リダイレクト、中継、遠隔設定、自己更新、動的なコード取得がないか。誰に何を送るか説明できるか。
- APIキー、Cookie、画面、写真、ファイル、会話やログが、本人の選んだ用途以外で扱われないか。
- ユーザー補助、通知、ストレージ、root、送信・購入・削除などの承認が拡大・迂回されていないか。
- Gradle、GitHub Actions、シェル、Python、JavaScript、JNI、同梱Linux環境、依存ライブラリに不審な処理がないか。
- AIへの指示文、内蔵知識、スキルが、情報送信や承認回避を誘導していないか。
- ライセンス、著作権表示、対応ソースが維持されるか。追加バイナリの出所・ソース・署名・ハッシュを確認できるか。

AIレビューには監査対象を読む役割を与え、指示の実行や秘密情報へのアクセスを与えません。AIの「問題なし」だけで承認しません。依存関係のチェックサムは取得物の一致を確かめるもので、処理の安全性を保証しません。不明点が解消しなければ保留し、機能と依存の一部だけを無理に取り込みません。

### 3. 日本語版の取り込みPRを検証する

一時ブランチで競合を解決し、日本語表示・日本語回答、中国系サービスの既定無効、手動の接続情報の保持、フォーク専用の更新先、権限・承認処理を維持します。[日本向け調整](JAPAN_TUNING.md)が既存方針の説明です。

上流SHAの監査後、取り込みPRの最終SHAも監査します。sourceをorigin、比較元を取り込み前のmainのSHAに変えて差分確認を実行します。監査済みの候補が変われば、その変更分も確認し、以前の結果を流用して承認しません。

既存のLinux CIでJVM・Android・CLIを検証します。動作確認はテスト用の端末・エミュレーター、ダミーの認証情報とデータから始めます。通信先・送信内容を観測し、アプリ起動、AI処理、サンドボックス、更新確認など、変更した経路を確認します。実際の個人用アカウントやGalaxyのデータを最初の試験に使いません。

監査対象のGradleやスクリプトを動かす場合は、署名鍵や個人データのない使い捨てのGitHubホスト環境などを使います。CIの権限は最小にし、未信頼コードを権限の強いpull_request_targetや個人PCのself-hosted runnerで実行しません。上流のworkflow自体も監査対象です。[GitHubの安全な運用指針](https://docs.github.com/en/actions/reference/security/secure-use)を参照してください。

### 4. 採否と根拠を残す

採用記録はdocs/upstream-reviews/に日付と候補SHAを含むMarkdownで残します。[記録のひな形](../tools/upstream/review-template.md)を使い、監査した最終SHA、採用・保留の理由、検査結果、未検証範囲、通信先の判断を記載します。

accepted_commitは、そのSHAまでの上流変更をすべて取り込み、または変更ごとの不採用理由を記録した場合だけ進めます。部分取り込みの段階で先のSHAへ飛ばすと、保留した変更を次回見落とすため、基準は進めず採用済みの個別コミットを記録します。監視は「全変更の採否を判断済み」の地点との差分を出します。

管理者がmainへ統合した後に一時ブランチを削除します。配布する場合は[公開手順](release.md)に従い、監査済みのmainから署名・対応ソース・チェックサムを作ります。上流のAPKや未監査のバイナリを、そのままMika JPの配布物にしません。

## mainの保護

GitHub側ではmainの更新をPR経由に限定し、最新のmainに対するupstream-toolsとandroid-and-jvmの検証成功、レビュー上の会話の解決を必須にします。管理者にも適用し、force pushとブランチ削除を禁止します。単独保守のため他人の承認を必須にはせず、管理者が監査記録を読んで統合を判断します。CIの成功が人の監査や通信確認の代わりになるわけではありません。

これはGitHubの設定であり、ソースだけでは有効状態を確認できません。SettingsのBranchesとmainの保護状態で定期的に確認します。監視・監査・CIの設定変更自体もセキュリティに影響する変更としてレビューします。

## 現在の自動化の範囲

この仕組みが自動化するのは、日次検知、監査待ちIssueの集約、固定SHAの差分取得と棚卸し、棚卸しツール自身のテストです。AIによる週次作業は別途登録するCodexタスクで行います。安全性の判定、テスト用データでの通信確認、mainへの採用、署名・公開は検知ワークフローに任せません。

CodeQL、Gradle依存関係の署名・チェックサム検証、端末通信の回帰検査は、この変更では導入していません。追加する際は、既存の取得物を信頼できるか確認してから基準を作り、検査を通すためだけに上流の新しいチェックサムを自動承認しません。
