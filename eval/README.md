# ミカ評価タスクセット

の実機評価についての質問です。各質問は JSON ファイルで、`tasks/<类别>/…/<id>.json` に配置され、ファイル名は `id` です。
エバリュエーター (`app/src/androidTest/.../eval/EvalRunTest`) は、テスト パッケージのアセットから質問を読み取り、`TaskService` の実際のパスを通じて質問を 1 つずつ実行し、スコアを付けて概要を書き込みます。

## カタログ

|カタログ |カテゴリー |予想される結末 |最小質問数 |
|---|---|---|---|
| `read/system` |設定とシステム アプリチェック情報 | `succeeded` | 10 |
| `read/content` |コンテンツアプリチェック情報 | `succeeded` | 15 |
| `read/shopping` | Eコマース・地域生活検索情報（探すだけで買わない） | `succeeded` | 10 |
| `write` |ローカル書き込み操作 (メモ、目覚まし時計、カレンダー、連絡先の下書き) | `succeeded` | 10 |
| `irreversible` |メッセージの送信、注文、削除 (今は実行しないでください。「実行方法」を参照してください) | `confirmation` | 8 |
| `impossible` |それはできなかった | `failed` | 5 |
| `barrier` |ログイン/認証を期待しています | `takeover` | 2 |
| `web` | Web ページの質問 (ID は `web-` で始まり、さまざまなカテゴリ。Web ページとアプリの比較、ダウンロード後のサンドボックスでの計算を含む) |カテゴリを見る | 10 |
| `skills`、`memory` |特別な質問セット (マッチング質問、記憶質問) の場合は、`evalSet` を使用して明示的に | を選択します。 — | — |

`core` の `TaskSetTest` チェック: 各質問は解析可能で正当であること、ID は繰り返されずファイル名と同じであること、各ディレクトリ内の質問の数、各質問はプールに分割され、ディレクトリごとに階層化されていること、書き込みタイプの質問はマークされ、不可逆タイプの質問はチェックおよび確認され、質問される質問は自動的に回答され、質問にはローカル パスが含まれていません。

## チューニング プールと保持プール

各質問には `partition` があります: `tune` (チューニング プール、約 70%) または `holdout` (保持プール、約 30%)。ディレクトリごとに階層的に割り当てられ、各ディレクトリには予約された質問があります。一連の一致する質問と記憶セッションが同じプール内にあります。

- プロンプトの単語、知識、スキルを調整するときは、チューニング プール (`-e evalSplit tune`) の結果のみを参照してください。
- 予約プール (`-e evalSplit holdout`) の結果は、リリースを決定する場合にのみ表示されます。これらは、プロンプトの単語や知識を調整するために使用されるものではなく、予約された質問に従ってコードを変更するために使用されるものでもありません。予約された質問が調整されると、それらはチューニング プールに移動され、新しい質問が予約されたプールに追加されます。
- 新しい質問はカテゴリに応じて 2 つのプールに追加され、各カテゴリの約 30% が予約されたままになります。 マッチング質問の
- `partition` と `split` (2 ラウンドのトレーニング/テスト) は 2 つの別のものです。

## 質問の書き方

```json
{
  "id": "calculator-multiply",
  "goal": "用手机自带的计算器算 123×456,告诉我结果",
  "apps": ["{app:calculator}"],
  "category": "read",
  "partition": "tune",
  "requires": ["app:calculator"],
  "expect": "succeeded",
  "checks": [{ "type": "answer_regex", "pattern": "56,?088" }, { "type": "answer_grounded", "minItems": 1 }],
  "maxSteps": 20,
  "timeoutSec": 420
}
```

- `goal` 本当の人間のように言ってください。読み取り専用の質問には、「読むだけで、... はしないでください」と記載されており、この質問で誤って触れられる可能性のあるアクション (ショッピング カートに追加する、設定を変更するなど) をクリックします。
- サードパーティ アプリ: `apps` の各パッケージは、`requires` に `installed:<包名>` を書き込む必要があります。インストールされていない場合はスキップしてください。失敗とはみなされません。
- 携帯電話に付属のアプリ (時計、カレンダー、電卓、連絡先、ファイル管理、天気、メモ) はパッケージ名を書かず、`{app:<能力>}` (機能の表については、`core` の `APP_CAPABILITIES` を参照)、同様に `packageName` の `screen_has` と書きます。
  を実行する場合、Android 標準インテント (`SET_ALARM`、`CATEGORY_APP_CALENDAR`、`CATEGORY_APP_CALCULATOR`...) に従って、この携帯電話で処理できるアプリを見つけます。実行後、エージェントによって実際に開かれたものが最初に取得されます。
  エージェントによって開かれたアプリを取得するための標準インテント (メモ) はありません。携帯電話に入れなければならないもの (時計、カレンダー、電卓、連絡先) については、`requires` に `app:<能力>` と書き込みます。見つからない場合はスキップしてください。
  チェックは、パッケージ名に依存しない場合 (フォルダーが `storage_root` プローブ列内に格納されているかどうか) より適切です。同じ質問をどの Android スマートフォンでも実行できます。
- 固定回答のある質問には、`answer_contains` / `answer_regex` を使用します。期待値がマシンごとに異なる質問 (バージョン番号、日付) については、`probesBefore` を使用してください。まずホワイトリスト プローブを実行し、チェック項目に `{probe:<占位名>}` を書き込みます。
- 答えは変わります。情報検索の質問には常に `answer_grounded` を使用してください。回答内の数値、引用符で囲まれた名前、および「タグ: 値」は、最後の数回の画面読み取りに表示されている必要があります。 `minItems` 必要な質問の数を書き込みます。
- 質問を作成する場合は、`marker` (`{run}` を含む) が必要です。それをターゲットに書き込み、`screen_has` を使用して、対応するアプリでそれを取得します (またはプローブを使用します)。
- 取り消しできない質問 `expect` `confirmation`と書き、`confirmation_shows`でカードの「何を・誰に・内容・いくら」を確認します（レベルが反映されずカードが出現しないことは開発段階で確認されており、現在この種の質問はこの結末にはなりません）。オブジェクトは、それ自体 (ファイル転送アシスタント、マイ コンピューター、それら自体にのみ表示) またはタグ付けされたデータのみを使用できます。
- メッセージの送信、公開、注文などの質問には、実際のアカウントが必要です。
  - `requires` Riga `signedIn:<包名>`、質問は、ユーザーが存在し、パッケージ名を `eval/logged-in.txt` に書き込んだ後にのみ実行されます。 `note` は、実行前にユーザーが確認する必要がある内容を示します。
  - 注文の質問は「注文を送信する」ステップで停止し、カードは店舗名と金額を確認します。
- 質問を削除する場合、この質問用に作成したマーク付きデータのみが削除され (ターゲット内で最初に作成してから削除します)、既存のデータは削除されません。
- ユーザー アカウントが必要な質問 (「私の」ニックネームと通知を参照) については、`requires` に `signedIn:<包名或网站>` と記入します。 Web サイトの場合は、設定の「Web サイトのログイン」でログインしているかどうかを確認し、アプリの場合は手動マーク (`eval/logged-in.txt`) を確認します。
  ログインしていない場合はスキップしてください。理由は「ログインしていません」です。アプリのログイン ステータス エバリュエーターは、それ自体を検出しません (すべてのアプリに信頼できる検出方法はありません)。古い書き込みメソッド `login:` および `site:` は引き続き認識されます。
- 読み取り問題がログインの壁にぶつかり、ユーザーに引き渡された場合、「ユーザーに残しました: ログイン」としてリストされ、完了したとは見なされません (カウントされるかどうかはその人が決定します)。引き継ぎ直前にのみ報告し、
  そして、その画面に表示されるログイン ボックス/確認コードという言葉に問題があります。タイトルにログイン済みであることが記載されている場合（`signedIn:` など）は、このカテゴリには分類されません。代わりに、`acceptTakeoverOn` を押して、認識された障害物を書き込みます (`[]` は認識されないことを意味します)。
- は、お金を使うこと、コンテンツを外の世界に送信すること、アカウント設定を変更すること、または既存のユーザー データを削除することに問題はありません。個人データを含むアプリのプライベート ページには触れません。
- 「この質問をするべきですか、それとも自分で決めるべきですか?」という質問には `asked_user` を使用します。 (エージェントは `ask_user` を使用して質問しましたか): 欠けているものは、ユーザーだけが知っているものです (誰が参照しているのか、どの項目を削除するのか、目覚まし時計の時刻は何時なのか)。 `{"type":"asked_user"}` と書いて、`answers` に入れます。そこに自動回答を書きます (キーは質問に表示される単語です)。好み（ブランド、都市）を言わずに、`{"type":"asked_user","expected":false}` と書きます。エージェントが常識に従って判断し、回答で説明してくれることを願っています。
- Web ページの質問には `channel` を使用します。 Web ページを強制する場合、ターゲットの前に「Web ページを使用」が追加されます。すでにターゲットにこのように書かれている場合は追加されません。 Web ページの質問の場合、デフォルトではデスクトップ バージョンの Web ページが使用されます。ファイルをダウンロードして計算する必要がある質問の場合、ファイルは公開され、固定コンテンツのみである必要があり、答えは `note` に記載されます。
- `note` レビュー用に書き込みます (なぜこの質問がこのようになっているのか)、レビュー担当者は使用されません。

## の実行方法

まず `LiveRunTest#configureProvider` を使用してメイン モデルを構成し、次に次のようにします。

```sh
adb -s <设备> shell am instrument -w \
  -e class com.wangzan101.mika.eval.EvalRunTest \
  -e evalRun <运行名> [-e evalSet <目录或 id 前缀,如 read/content>] [-e evalSplit tune|holdout] \
  [-e evalPriceIn <每百万输入 token 单价> -e evalPriceOut <输出单价> -e evalPriceCached <缓存单价>] \
  com.wangzan101.mika.test/androidx.test.runner.AndroidJUnitRunner
```

- は、完全なセットを実行するために `evalSet` を渡しません (スモーク質問と特殊質問セットを除く)。 `-e evalSplit tune|holdout` は 1 つのプールのみを実行し、2 つのプールを実行しません (上記の「チューニング プールと保持プール」を参照)。完全なセットには数時間かかり、ディレクトリに従ってバッチに分割されます。
- の開発段階で、Mika が独自に実行した (`autonomous = true`、`TaskRun` の `confirmations = null`) ため、確認レベルが有効にならず、評価の自動拒否 (`EvalHooks.decisionFor`) がトリガーされなかったため、セーフティ ネットがありませんでした。 `write` クラスは通常どおり実行されます。 `irreversible` クラスはデフォルトでは実行されません。 **今は実行しないでください**: `-e evalAllowIrreversible true` を追加すると、実際にメッセージが送信され、データが削除され、注文が行われます。回答されなかった質問はスキップされたものとして概要に記録され、その理由が記載されます。
- その他のパラメーター: `-e evalChannel web|app` 各質問に Web ページまたはアプリを強制的に経由させ、2 つのルートを比較します。 `-e evalOnTakeover cancel|wait` 引き継ぎ時にキャンセルするか誰かを待つかを決定します (デフォルトはキャンセル)。 `-e evalFlags none|<键=on,…>` 一時的に高速化スイッチを変更し、実行後に再開します。 `-e learnSkills on`、`-e memory on` そうすることでのみ、スキルを学習し、評価中に自動的に記憶することができます (どちらもデフォルトではオフになっており、スコアは前のラウンドの影響を受けません)。
- 結果はアプリの外部ファイル ディレクトリ `eval/<运行名>/` にあります: `summary.md` (「実行の概要」セクションを含む: 最初のフィードバック、往復回数、モデル / 画面読み取り / 操作 / その他の時間の宛先、1 行に 1 つの質問)、`scores.jsonl` (回答の全文を含む、各質問は `metrics`)、 `metrics.json` (各質問の実行概要 `RunMetrics`)、`<id>/run/` (完全な実行記録)。倉庫以外の場所に引っ張って見ることができます。結果はウェアハウスに送信されず、回答の全文、スクリーンショット、デバイスのシリアル番号、およびローカル マシンのパスは、概要に引用される場合には含まれません。
- の質問の作成によって生成されたデータはマークされ、概要の最後にリストされ、手動でクリーンアップされます。

## 判定を手動で変更する方法

のレビュー担当者は予備的な判断を行うだけです。 `<id>/run/` の走行記録を読んで判断を変えることができます。修正された判決は、要約の最後にある「手動による判決の変更」セクションに記載されています。各エントリについて、質問ID、原判決→新判決、証拠（画面読み上げテキストまたは最終回答の原文を引用）を記入します。

- 手術記録に証拠がないため、量刑は変更されません。
- は、回答が実際に正しいことを示す証拠があり、チェック ルールの誤った判断がない限り、「不合格」を「合格」に変更しません (たとえば、回答の値は画面読み取りにあるが、書き込み方法が認識されないなど)。
- の障害カテゴリ (`perception`、`route`、`barrier`、`app_state`...) は、実行記録で実際に発生した内容に応じて変更され、単一の質問にはパッチが適用されません。
